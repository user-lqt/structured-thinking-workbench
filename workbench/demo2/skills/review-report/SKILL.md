# 复盘报告

## 何时使用

活动结束后总结时。包括「复盘」「总结报告」「这次做得怎么样」。

## 输入

项目信息表（含核心目标、预算）+ 任务分解表（含完成度、状态）+ 风险台账与处置情况 + 现场记录 + 阶段检查点完成情况。

## 输出契约

章节由调用方注入，逐字对齐。归因部分必须用结构化框架，不要写成散文。

## 各章要求

| 章节 | 必须包含 |
|---|---|
| 一、活动概况与目标达成 | 活动基本信息回顾；**逐条对照核心目标**判定达成 / 部分达成 / 未达成，并给判断依据 |
| 二、数据回顾 | 报名数 / 到场数 / 到场率 / 各阶段任务完成率 / 预算执行情况（未取得数据的写 `待补充`） |
| 三、做得好与不足 | 两栏对照：做得好的三条（含可复制做法）、不足的三条（含具体表现） |
| 四、问题归因分析 | 用「现象 → 直接原因 → 根本原因 → 归类」四列表格；归类维度：计划 / 组织 / 资源 / 沟通 / 外部 |
| 五、改进措施与责任分工 | 问题 / 改进措施 / 责任角色 / 完成时限 / 验证方式 |
| 六、下次可直接复用的清单 | 可直接复用的物料、模板、流程、渠道，逐条列出 |

## 写作要求

- 目标达成判定必须有依据，不能只写「基本达成」
- 归因要区分直接原因与根本原因；「时间紧张」通常不是根本原因
- 不足的部分要写具体现象，不要写「配合还不够默契」这类模糊表述
- 改进措施要可验证，写明验证方式
- 数据缺失时写 `待补充`，不得编造数据

## 事实边界

- 不得编造参与人数、满意度、媒体报道
- 不得编造未发生的失误与成绩
- 数据一律来自任务分解表、风险台账与现场记录

## 验收清单

- [ ] 输出是合法 JSON，章节与注入模板逐字一致
- [ ] 核心目标逐条判定并给出依据
- [ ] 归因表区分直接原因与根本原因
- [ ] 未编造人数、满意度与媒体数据

## 交付格式

- **主交付**：Word 文档（`.docx`）。章节标题映射为标题样式，Markdown 表格映射为 Word 表格。
- **备选**：Excel（`.xlsx`）与 Markdown（`.md`）。
- **导出入口**：「过程材料」卡片上的 `Word` / `Excel` / `Markdown` 按钮（`Word` 为主按钮），或页头的「导出材料包（Word）」。程序内对应 `window.WB.exporters.materialToDocx(doc)` / `materialToXlsx(doc)`。
- **写作要求**：用标准 Markdown 组织正文——空行分段、`-` 列表、必要时用一张管道表格；只有「本章本身就是清单 / 明细」时才用表格，说明、规则、流程、职责一律写段落。不要写 HTML，导出时只识别这些结构。
