# 风险台账与分级应急预案

## 何时使用

项目信息表与任务分解表已建立，需要识别风险、评估等级、准备应急预案时。

## 输入

项目信息表（含人数、场地、预算、审批要求）+ 任务分解表（挂靠对象）+ 已勾选产出。

## 输出契约

```
{
  "risks": [
    {
      "name": "风险名称，12 字以内",
      "category": "safety|health|venue|tech|program|weather|finance|compliance|publicity|participation",
      "phase": "plan|prepare|execute|close",
      "task": "任务分解表中的任务名称",
      "probability": 1-5,
      "impact": 1-5,
      "trigger": "可观察的预警信号",
      "prevention": "预防措施",
      "response": "现场响应动作",
      "escalation": "升级路径与授权人",
      "owner": "负责角色"
    }
  ],
  "compliance": ["合规提示，最多 3 条"]
}
```

分值由调用方按 `可能性 × 影响` 自动计算，不要输出分值与等级。

**输出前必须先完成打分校准，不要一上来就写 JSON。**

`risks` 数组**必须按分值从高到低排列**，并按下表核对各段数量：

| 位置 | 等级 | 分值 | 数量 |
|---|---|---|---|
| 最前面 | 高 | 15–25 | 2–4 项 |
| 中间 | 中 | 8–14 | 6–11 项 |
| 最后面 | 低 | 1–7 | 3–5 项 |

排好序后自问：最前面那几项真的严重吗？最后面那几项真的可以忽略吗？不符就重新打分：

- 直接影响人身安全、活动能否举办、是否违规的，应该排在最前面
- 只是体验欠佳、流程不顺畅的，应该排在最后面

**3 不是默认值。** 「同类活动偶有发生」才是 3，「较为常见」是 4，「已具备苗头、几乎必然」是 5。影响同理：不影响主体流程是 2，当天可恢复是 3，导致环节取消或明显超支才是 4。只有极少数风险配得上 5 分影响。

## 风险分类

按这十类逐一排查，不要只挑显眼的几类：

| 类别 | 代码 | 典型风险 |
|---|---|---|
| 安全与秩序 | `safety` | 人群拥挤踩踏、通道阻塞、消防隐患、治安冲突 |
| 人员与健康 | `health` | 中暑、受伤、突发疾病、医疗救助不及时 |
| 场地与设施 | `venue` | 场地临时不可用、容量不足、设施损坏、用电超负荷 |
| 技术与网络 | `tech` | 音视频故障、直播中断、网络不可用、系统崩溃 |
| 内容与流程 | `program` | 嘉宾缺席、流程延误、赛制争议、评分争议 |
| 天气与环境 | `weather` | 降雨、大风、高温、空气质量 |
| 财务与物资 | `finance` | 超预算、物资未到位、结算争议、赞助违约 |
| 合规与审批 | `compliance` | 未批先办、安全许可缺失、肖像权与隐私、版权 |
| 宣传与舆情 | `publicity` | 宣传失实、报名信息错误、负面舆情 |
| 参与与体验 | `participation` | 报名不足、到场率低、投诉集中、体验落差 |

## 评分锚点

**可能性 P**

| 值 | 含义 |
|---|---|
| 1 | 极低：同类活动几乎未出现过 |
| 2 | 较低：有先例但罕见 |
| 3 | 中等：同类活动偶有发生 |
| 4 | 较高：同类活动较为常见 |
| 5 | 很高：当前条件已具备苗头，几乎必然发生 |

**影响 I**

| 值 | 含义 |
|---|---|
| 1 | 极低：可忽略 |
| 2 | 较低：轻微影响，不影响主体流程 |
| 3 | 中等：影响部分环节或体验，当天可恢复 |
| 4 | 较高：导致环节取消、明显超支或参与人数显著下降 |
| 5 | 很高：人身安全事件、活动终止、重大舆情或合规事故 |

## 分级与响应

- 分值 = P × I，范围 1–25
- **高：15–25** —— 活动总协调立即介入；涉及人身安全先暂停或疏散，通知校方保障或急救；未经风险复核和负责人确认不得恢复
- **中：8–14** —— 责任人执行预防或替代方案，向总协调报告进度；超时或影响扩大时升级为高风险流程
- **低：1–7** —— 责任人跟踪并记录；触发条件改变时重新评估可能性与影响

## 应对策略（4T）

写预防与响应时，说明属于哪一种：

- **规避 Avoid**：改变方案，直接去掉风险源
- **减轻 Mitigate**：降低可能性或影响
- **转移 Transfer**：保险、外包、报备学校或公安
- **接受 Accept**：记录并监控，准备好应急动作

## 升级链

发现人 → 任务负责人 → 现场总协调 → 活动组织者 → 校方保障 / 相关部门（必要时 110 / 120 / 119）

`escalation` 要写明：**触发升级的条件**、**升级对象**、**谁有权决定暂停或恢复**。

## 覆盖要求

- 四个阶段都要覆盖，每阶段至少 2 项
- 总数 12–18 项
- 高风险（15–25）至少 2 项，但不超过 5 项——不要把所有风险都打成高风险
- 至少 1 项合规类风险
- 户外活动必须有天气类风险；室内活动改为用电与消防类风险
- 每项风险都要能挂到任务分解表里的某个任务上
- `task` 只填任务名称本身，**不要带阶段、负责人或竖线连接的前缀**
  - 错误：`前期策划｜编写活动策划书｜策划组`
  - 正确：`编写活动策划书`
- 评分必须满足输出契约处的目标区间

## 事实边界

- 不得编造具体人名、电话、单位、数据
- 责任人写角色（现场总协调 / 后勤组 / 宣传组…），不知道人名就写角色
- 缺少依据的联络方式、备用场地一律写 `待确认`

## 验收清单

- [ ] 输出是合法 JSON，顶层只有 `risks` 与 `compliance`
- [ ] 四个阶段都有风险，每阶段不少于 2 项
- [ ] 每项风险的 `task` 都能在任务分解表中找到，且不带阶段或负责人前缀
- [ ] 高风险数量在 2–5 项之间，中档不超过 8 项
- [ ] 每项都写全了触发信号、预防措施、现场响应、升级路径
- [ ] 未编造人名与联系方式

## 交付格式

- **主交付**：结构化表格导出（Markdown / CSV），由所在视图的导出按钮生成。
- **说明**：本技能维护的是工作台内的结构化数据，不产出可下载的文档；需要 Word / Excel 时，请到「过程材料」导出对应材料。
