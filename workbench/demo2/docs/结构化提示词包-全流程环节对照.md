# 第一部分 · 项目结构化任务书（总纲）

> 本节按 `structured-brief` 的固定八节输出，回答「整个项目是怎么被结构化的」；第二部分才是「每个环节具体说了什么」。

## 1. 需求复述

你要的是：在**不引入任何第三方依赖、不破坏 demo2 现有功能**的前提下，把 `workbench/demo2` 从「填表 + 导出」升级成**覆盖策划-筹备-执行-收尾全周期、产出物可由用户自由组装**的管控工作台，并配齐用户手册、验证记录与提交材料。

含糊处（按要求不自行假设，全部进第 7 节）：

| # | 含糊处 | 为什么不猜 |
| --- | --- | --- |
| 1 | 「优化」的验收口径未定（修 bug？加功能？重构？） | 三种口径的工作量差一个数量级 |
| 2 | 改动范围边界（能否动 demo2 以外的目录） | 误改会污染他人文件 |
| 3 | 可自主执行到什么程度（要不要逐步确认） | 决定是否每步停下来等确认 |
| 4 | 活动是单日还是多日 | 直接决定数据模型怎么建 |
| 5 | 最终交付物清单与组内分工 | 报告的分工章节无法写实 |

## 2. 目标与成功标准

**目标（1 条，可衡量）**：在零构建、零第三方依赖、不破坏既有功能的前提下，把 demo2 升级为覆盖**策划 / 筹备 / 执行 / 收尾**四阶段、且**产出物可按需自由组装**的活动管控工作台，并产出用户手册与可复现的验证记录。

**成功标准（4 条，均可核验）**：

1. 全周期四阶段每一阶段都有可操作视图 + 可导出的中间产物（打开工作台数一遍即可判断）；
2. 过程材料能**逐章指定形式**（哪一章写正文、哪一章写表格），导出结果不是整篇表格；
3. 产出配置能由用户自由组装（含自定义技能包：按约定格式放一个文件即进配置），**不改源码即可生效**；
4. 验证全绿 + 真机走查通过：`node tools/selftest.mjs` 失败 0 项；端到端模拟用户走查无阻断性缺陷。

**非目标（3 条，明确不做）**：不做登录与权限体系；不引入 Vue / React / 打包器等构建链（零构建是硬约束）；不做服务端数据库与多用户并发。

## 3. 约束分层

**硬约束（不可协商）**

| 类别 | 内容 |
| --- | --- |

**第一层维度：流程步骤（工作推进顺序）** —— 八环节按时间先后排列，顺序本身有含义（金字塔「逻辑递进」）。
**第二层维度：各环节按自身性质另选维度**，每张卡下方标注。

```

├─ 1 需求界定与目标定位           第二层维度：5W2H
├─ 2 授权边界与环境自检           第二层维度：约束类型（系统 / 工具 / 流程）
├─ 3 概念澄清与信息架构           第二层维度：术语 → 关系 → 操作
```

## 5. 方案比较与决策

三个候选方案（差异真实，不是同义改写）：

| 方案 | 做什么 | 范围 | 风险 |
| --- | --- | --- | --- |
| **A 微调** | 只修 bug + 界面微调，不加新机制 | 最小 | 低 |
| **B 加法式改造** | 保留现有架构，新增视图与技能包机制、卡片工作流 | 中 | 中低 |
| **C 换 Vue 重写** | 引入构建链，前端整体重写 | 大 | 高 |

评估维度 5 个、权重合计 100%（评分为 1–5 分，**全部标注「估算」**，非实测）：

| 评估维度 | 权重 | A 微调 | B 加法式改造 | C 换 Vue 重写 |
| --- | --- | --- | --- | --- |
| 达标程度 | 35% | 2.0 | 4.5 | 5.0 |
| 与硬约束相容 | 25% | 5.0 | 5.0 | 1.0 |
| 组内可维护性 | 20% | 4.5 | 4.0 | 2.0 |
| 工期可控 | 10% | 5.0 | 3.5 | 1.5 |
| 演示效果 | 10% | 2.0 | 4.5 | 4.5 |
| **加权合计** | 100% | **3.55（估算）** | **4.43（估算）** | **3.00（估算）** |

**结论**：选定 **B（加法式改造）** —— 它在权重最高的「达标程度」上接近满分，同时完全兼容硬约束。
**放弃 C 的理由**：与「零构建零依赖」硬约束直接冲突（该维度仅得 1.0），且工期不可控。
**放弃 A 的理由**：达标程度不足，无法满足「全周期 + 可自由组装」两条成功标准。
**若假设不成立则切换**：若组内可投入时间不足 2 人 × 3 天，降级为「A + 只做产出配置自由组装」。

## 环节 1 · 需求界定与目标定位

**本环节维度**：5W2H（把一句话需求缺的要素扫全）

**① 原始提问（原话照录）**

> 「当前项目有demo2，你的任务就是优化demo」
> 「等一下」
> 「现有要求：在优化好demo2之前，请勿随便在其他文件夹添加文件。」

**② 结构化重写：这句话缺了哪些要素**

| 要素 | 原话里的状态 | 补成什么 |
| --- | --- | --- |
| 任务 | 有（优化 demo2）| 优化到什么程度、验收口径是什么 |
| 目标 | 缺 | 可衡量目标 + 成功标准 |
| 边界 | 口头限制（别乱加文件）| 写成硬约束：改动只落 `workbench/demo2/` |
| 非目标 | 缺 | 明确不做什么 |
| 优先级 | 缺 | 用 MoSCoW 排「必须做 / 应该做 / 可以做」 |

**③ 可整段复制的提示词（框架：RTGO + 硬软约束分列）**

```text
【角色】你是本项目的结对开发工程师，同时承担产品经理职责。
【背景】已有底稿 workbench/demo2（零构建、零第三方依赖）。我现在只说了一句「优化 demo」，信息不全。
【任务】先不要改任何代码。请把「优化 demo2」这句话补成一份可验收的改动清单，再停下来等我确认。
【要求】
1. 用 5W2H 逐项列出你没被交代的要素：为什么优化 / 优化什么 / 谁来验收 / 什么时候要 / 在哪里改 / 怎么算改完 / 改多少。
2. 约束分硬、软两栏写：
   硬约束 —— 只在 workbench/demo2/ 内改动；不新增任何第三方依赖；不改动文件名与目录结构；不提交 git；不破坏现有功能。
   软约束 —— 沿用现有代码风格与中文文档；改动尽量小、可回滚。
3. 至少给出 1 条非目标（明确不做什么）。
4. 输出格式：① 改动清单（按「必须做 / 应该做 / 可以做」分级）② 每条附一句验收判据（能一句话判断达成与否）③ 待确认清单（缺什么 / 问谁 / 不确认的后果）。
【禁止】不要自行假设缺失信息后继续推进；在我说「开始」之前不要写任何代码。
【缺信息处理】信息不足处标「待确认」，不要编造。
```

**④ 命中的结构化思维模型**

| 模型 | 用在哪一步 | 一句话说明 |
| --- | --- | --- |
| 目标定位（可衡量目标 + 可核验成功标准）| 第 2 节 | 「优化」这种动词不能验收，必须换成可判断的标准 |
| 非目标设定 | 第 2 节 | 把「不做什么」写出来，边界才闭合 |
| 约束分层（硬 / 软）| 第 3 节 | 时间·资源·规则·质量·伦理五类各扫一遍 |
| MoSCoW 优先级 | 第 2 节 | 资源有限时先做必须做的 |

**⑤ 产出与验收**：改动清单 + 验收判据 + 待确认清单。验收判据 —— 清单里每一条都能用一句话判断是否达成，且没有任何一条越出 `workbench/demo2/`。

**⑥ 可引用的阶段成果**：本次会话的全部改动最终都落在 `workbench/demo2/` 内（可直接用 `git status --porcelain` 的路径列表作证据）。

## 环节 2 · 授权边界与环境自检（让 AI 能自主干活）

**本环节维度**：约束类型（系统策略 / 工具能力 / 流程约定）

**① 原始提问（原话照录）**

> 「怎么让你能自己工作」
> 「不用点确定」
> 「你现在看看是否可以开始自主工作了？」
> 「看一下当前权限」
> 「现在呢」

**② 结构化重写：这句话缺了哪些要素**

原话是「我想让你少问几次」这种**诉求**，不是可执行指令。补法：把它拆成「先如实报告权限 → 再判断能否连续工作 → 最后给改法」，并要求读不到的项写「未知」而不是推测。

**③ 可整段复制的提示词（框架：RTGO + 前置条件核查清单）**

```text
【角色】你是能自查运行环境的开发助手。
【任务】如实报告当前会话的权限与环境，判断你能否「无人确认地连续工作」。不要先给建议，先给事实。
【输出格式】一张核查表，列固定为：| 核查项 | 当前值 | 从哪读到的 | 对「自主工作」的影响 |
核查项至少包含：
  1. 文件系统沙箱模式（有没有目录限制）
  2. 审批策略（每条命令都要确认 / 仅危险命令确认 / 从不确认）
  3. 网络访问是否可用
  4. 可用工具清单（读写文件 / 执行命令行 / 调用模型接口）
  5. 必须由用户手动做的事（例如删除目录、提交 git）
表后写一行结论：「可以自主工作」或「不可以，卡在 X」，再写「若要自主工作，需要改什么」。
【禁止】不要把「应该可以」写成「可以」；读不到的项写「未知」，不要推测。
【质量红线】只用实际读到的配置；缺项标「待确认」。
```

**④ 命中的结构化思维模型**

| 模型 | 用在哪一步 | 一句话说明 |
| --- | --- | --- |
| 约束分层（硬约束定位到具体层级）| 核查表 | 「无法自主」是现象，根因在系统策略层，不在「AI 懒」 |
| 前置条件核查清单（Checklist）| 第 1–5 项 | 把「能不能干」拆成 5 个可逐项验证的条件 |
| 权限矩阵 | 结论行 | 用「能 / 不能 / 需确认」三态代替模糊表述 |

**⑤ 产出与验收**：一张权限自检表 + 一行结论。验收 —— 结论可复现：照着表自己再查一遍，能得到同样结果。

**⑥ 可引用的阶段成果**：把「AI 能不能自主干活」从一个感觉问题变成了一份可核查的环境报告。

## 环节 3 · 概念澄清与信息架构

**本环节维度**：术语 → 关系 → 操作（先定义，再连线，最后给路径）

**① 原始提问（原话照录）**

> 「现在产出配置是怎么样的？勾不勾选有什么关系？」
> 「产出 和 全周期任务有啥区别？或者说全周期任务是干啥的？」
> 「点击『批量生成已选材料』后，材料放在哪里了？」
> 「不能进行单个生成，和在线浏览吗？」
> 「在醒目的地方进行提醒能在过程材料修改。」

**② 结构化重写：这句话缺了哪些要素**

| 原话的形态 | 问题 | 补成什么 |
| --- | --- | --- |
| 三个概念混着问 | 同名不同义，越问越乱 | 强制「先定义 → 再关系 → 后操作」，不许跳步 |
| 「材料放哪了」 | 缺「存在哪 / 何时失效」 | 术语表加「存放位置 + 生命周期」两列 |
| 「能不能单个生成」 | 缺「操作路径」 | 加一张「我想做的事 → 点哪里 → 做完在哪看」表 |

**③ 可整段复制的提示词（框架：ALIGN —— 把「写到哪里为止」写死）**

```text
【背景】工作台里有「产出配置」「全周期任务」「过程材料」三组概念，我分不清它们的关系。
【任务】按「先定义 → 再关系 → 后操作」三段回答，不许跳过前两段直接给建议。
【第 1 段 · 术语定义】逐个说明：它是什么 / 由谁产生 / 存在哪里（内存、存档、导出文件）/ 生命周期（何时出现、何时失效）。用表格。
【第 2 段 · 关系】用一张表说明两两关系：包含 / 并列 / 派生；并指出哪个是「单一事实来源」，哪些只是它的投影。
【第 3 段 · 操作路径】给一张表：| 我想做的事 | 在哪一步做 | 点哪个按钮 | 做完在哪里能看到 | 常见坑 |，至少 6 行。
【输出格式】三段，每段一张 Markdown 表格。
【禁止】不要用「等等」「之类」这类含糊词；不确定的项写「待确认」。
【缺信息处理】代码里读不到的事实就明说读不到，不要按常理推断。
```

**④ 命中的结构化思维模型**

| 模型 | 用在哪一步 | 一句话说明 |
| --- | --- | --- |
| 术语对齐（同名不同义是沟通事故源头）| 第 1 段 | 「产出」与「全周期任务」是两条不同的轴 |
| MECE 分类 | 第 1 段 | 产出 = 交付物维；全周期任务 = 时间维；两轴不正交就会重叠 |
| 5W1H 扫要素 | 第 1 段 | 补上「在哪 / 何时」两个被漏掉的要素 |
| 单一事实来源与投影 | 第 2 段 | 区分「真数据」与「由它算出来的展示」|

**⑤ 产出与验收**：三张表（术语 / 关系 / 操作路径）。验收 —— 看完三张表，能自己回答「勾不勾选有什么区别」而不需再问。

**⑥ 可引用的阶段成果**：这一轮澄清直接导致后续两个改造 —— 「材料生成后可在线浏览与编辑」和「材料改动必须有醒目提示」。

## 环节 4 · 模块化分解与技能包契约

**本环节维度**：耦合度（可独立复用 / 与工作台强耦合）—— 一刀切下去

**① 原始提问（原话照录）**

> 「将这些项目模块化包装，能拆解成单独skill的，就直接打包成skill，与工作台耦合较深的就直接固定就行。然后实现一个这样的功能：自定义skill添加，约定一类格式，让工作台能通过识别这个格式来增加产出配置里的项目。模块化，让用户可以自由组装，如何？」
> 「自定义部分能加个删除的功能吗？」
> 「我看网上有些skill都有脚本部分，script，我们这个项目有哪些东西是需要脚本的？」

**② 结构化重写：这句话缺了哪些要素**

原话已经自带 MECE 意识（「能拆的拆，耦合深的固定」），缺的是：**判定准则**（怎么算「能独立」）、**契约字段**（格式到底约定什么）、**校验**（格式写错了会怎样）、**取舍依据**（什么时候才真的需要 script）。

**③ 可整段复制的提示词（框架：RTGO + 接口契约 + 追加约束）**

```text
【任务】把现有产出物做一次模块化拆分，并给出「用户自定义扩展」的契约。
【第 1 步 · 分类】按「耦合度」这一维度，把当前所有产出物分成两类，逐条给出判定依据（是只依赖输入数据，还是依赖工作台内部状态）：
   A 可独立复用 —— 打包成独立技能包
   B 与工作台强耦合 —— 固定在代码里，不拆分
【第 2 步 · 契约】为 A 类定义一份「自定义技能包格式」，必须写清：文件名与目录约定、必填字段（唯一标识、名称、适用阶段、产出分类、提示词正文）、可选字段、占位符语法、出错时的降级行为。
【第 3 步 · 校验】列出格式非法时的三种典型情形（缺必填字段 / 标识重复 / 目录放错）及各自的提示文案。
【第 4 步 · 脚本判定】逐条回答「哪些部分真的需要 script」：给出「需要」的判定条件（必须访问文件系统 / 必须批量转换 / 必须联网）+ 逐项结论；不需要的写「不需要」并说明理由。
【输出格式】四张表：分类表 / 契约字段表 / 校验情形表 / 脚本判定表。
【约束】不新增第三方依赖；自定义技能包必须做到「放一个文件即生效，不改源码」。
【禁止】不要为了「看起来专业」而引入脚本层；不要编造不存在的字段。
【缺信息处理】读不到的写「待确认」。

—— 下一轮只需追加这一句（追加约束，不重写全文）——
【追加约束】在上一版基础上补三点：1）自定义条目要能删除；2）新增自定义入口的位置往右调，与已有按钮对齐；3）删除时要处理被它引用的地方，不允许留下悬空引用。其余保持不动。
```

**④ 命中的结构化思维模型**

| 模型 | 用在哪一步 | 一句话说明 |
| --- | --- | --- |
| MECE 分解（按耦合度一刀切）| 第 1 步 | 同层同维度，且两类互斥、合起来等于全集 |
| 接口契约收敛 | 第 2 步 | 让「格式」成为双方都遵守的约定，而不是各自猜 |
| 依赖分析 | 第 4 步 | 判断「是否真需要脚本」，而不是跟风加 |
| 追加约束迭代 | 末尾 | 在上一版上改，不重写全文 |

**⑤ 产出与验收**：技能包清单（28 个：8 个结构技能 + 20 类产出 —— 9 份文档、10 张表格、1 张图形）+ 自定义技能包格式规范 + 校验规则。验收 —— 手写一个自定义技能包文件丢进目录，刷新后产出配置里出现该项，删掉后消失且不报错。

**⑥ 可引用的阶段成果**：产出配置从「写死在代码里」变成「用户可自由组装」，并给出了格式契约与校验降级行为。

## 环节 5 · 数据与呈现改造

**本环节维度**：对象（数据层 / 界面层）

**① 原始提问（原话照录）**

> 「二维码那个页面的布局，字体是贴着左边沿的，你调整到合适间距」
> 「位置还不太好看，往右挪一点」
> 「那些纯文本的，都改成能自定义修改的。和自定义添加的能操作除了删除之外的其他修改等操作」
> 「对了，活动日和活动开始与结束时间更改一下，有可能活动是很多天的呢？你修改下逻辑，能比较自由地选择活动时间为哪几天，那几天又是分别几点开始几点结束」
> 「或者这样来改动：新增一个活动安排，把具体时间段挪到那里，并可选填每个时间段有什么活动。在项目信息表里只用填哪几天。」
> 「截止与确认流程和截止与确认流程是一定会有的吗？能动态删掉吗？」

**② 结构化重写：这句话缺了哪些要素**

原话是**现象描述**（「贴左边沿」「往右挪」「能不能删」），缺的是：**改造维度**（往哪个方向拆）、**单一事实来源**（新字段和旧字段谁说了算）、**可变与固定如何区分**、**老数据怎么办**。

**③ 可整段复制的提示词（框架：ALIGN + 兼容性约束）**

```text
【背景】现在活动时间只能填一个日期 + 一对起止时间，实际活动可能持续多天；另外有些章节是固定必出的，有些其实可以不出现。
【任务】先别改代码。按三步给出改造方案，我确认后再动手。
【第 1 步 · 时间模型】把「活动时间」从一个时间点拆成两层：
   第一层 活动日期 —— 可多选，只回答「哪几天」
   第二层 活动安排 —— 每个时段含：日期、开始时间、结束时间、该时段做什么活动（最后一项选填）
   并说明：项目信息表只填第一层，第二层由它派生；原「活动开始/结束时间」改为由第二层投影生成，避免两个地方各说一套。
【第 2 步 · 可变与固定】列出当前所有章节，逐条判定「必选 / 可删」，并说明删掉后哪些地方要跟着变（序号、导出目录、被引用处）。
【第 3 步 · 兼容与迁移】老存档里只有单日时间，怎么迁移？给出兜底规则（读不到新字段时用什么值，绝不能让老数据打不开）。
【输出格式】三张表 + 一段结论；每张表都要有「改动点 / 影响文件 / 回归用例」三列。
【约束】不新增依赖；不破坏已有功能；改动只落 demo2 内；旧存档与旧项目包必须照常打开。
【禁止】不要顺手改无关代码；不要为了让新逻辑跑通而丢弃旧数据。
【缺信息处理】读不到的字段写「待确认」。
```

**④ 命中的结构化思维模型**

| 模型 | 用在哪一步 | 一句话说明 |
| --- | --- | --- |
| 结构维度重构 | 第 1 步 | 「时间」从一个点升成「轴 + 时段」两层 |
| 单一事实来源与投影 | 第 1 步 | 只存「哪几天」，起止时间是算出来的 |
| 可变 / 固定分离 | 第 2 步 | 必选章节与可删章节分开，删除要有连带处理 |
| 兼容性 / 迁移兜底 | 第 3 步 | 新结构不能把老数据变成废纸 |
| 对象维度（数据层 / 界面层）| 全篇 | 「字体贴边」「按钮往右挪」属界面层，与数据层改动分开处理 |

**⑤ 产出与验收**：字段表 + 迁移兜底规则 + 回归清单。验收 —— 建一个跨三天的活动，每天时段不同，导出后时间正确；删掉一个可选章节，导出不报错。

**⑥ 可引用的阶段成果**：活动时间支持多日 + 分时段活动安排（新增「活动安排」视图）；材料章节可增删且序号与导出自动重排；全部旧存档回归通过。

## 环节 6 · 生成质量改造

**本环节维度**：问题—原因—对策（把模糊感受拆成可复现用例）

**① 原始提问（原话照录）**

> 「感觉这个AI生成的过程材料好不灵活。逻辑就是直接把表格导出。但是实际中百分百不会一整个word全都是一行行的表格的，这不符合人类的习惯啊。还有，有时候就莫名其妙的，如那个报名页生成，为什么要生成那样的呢？并且：……（粘贴了一大段乱掉的表格内容）……这是什么内容啊？完全就不该在报名表中出现。你自己试试用一下看看效果，各个过程材料的skill还是得优化才行啊」

**② 结构化重写：这句话缺了哪些要素**

这一条**含 4 个独立问题**，混在一段话里：① 材料通篇铺表格 ② 某些产出「生成得莫名其妙」③ 出现了不该出现的内容（开发口径、空表格碎片）④ 要求 AI 自己先试一遍。补法：拆条 → 每条给最小复现用例 → 再归因 → 再对策。

**③ 可整段复制的提示词（框架：CO-STAR + 反例驱动）**

```text
【背景】工作台生成的过程材料质量不稳：整篇都是表格；《报名表》里出现「字段名 / 类型 / 是否必填 / 校验规则 / 用途」这种给开发者看的开发口径，还夹着一行一行的空表格碎片；某些产出生成得莫名其妙。
【受众】材料的读者是老师、同学、参与者 —— 不是程序员。这是判断内容该不该出现的第一标准。
【任务】不要先改代码，按「现象 → 归因 → 对策 → 验收」四步走。
【第 1 步 · 现象拆条】把我上面这段话拆成互不重叠的若干条缺陷，逐条给一个可复现的最小用例：在哪个产出、点哪个按钮、期望看到什么、实际看到什么。
【第 2 步 · 归因】每条缺陷归到以下三类之一，并给出依据（指出是哪个 skill / 哪段代码导致）：
   a) 提示词与契约层（没写清材料该写什么）
   b) 数据层（输入数据本身缺字段）
   c) 渲染与导出层（Markdown 与导出格式转换）
【第 3 步 · 对策】每条给一条最小改动对策，并标注影响面：只改 skill / 要改代码 / 要改数据结构。
【第 4 步 · 验收】给出可判断的验收判据：
   - 材料以正文为主体，表格只用于必须并列对比的信息；
   - 交付物一律站在读者视角，不出现开发口径（字段类型、校验规则、表结构、接口定义）；
   - 章节标题下不允许出现空表格。
【输出格式】一张主表：| 缺陷 | 最小用例 | 归因类别 | 依据 | 对策 | 影响面 | 验收判据 |
【禁止】不要用「优化一下」「更自然」这类无法验收的说法；不要声称已改好。
【缺信息处理】证据不足的归因写「待确认」，不要猜。
```

**④ 命中的结构化思维模型**

| 模型 | 用在哪一步 | 一句话说明 |
| --- | --- | --- |
| 问题—原因—对策 | 第 1–3 步 | 从「不好看」到「哪一段代码导致的」 |
| 质量维度（完整 / 准确 / 时效 / 合规）| 第 4 步 | 验收标准必须可判断 |
| 反例驱动 | 第 1 步 | 把坏的输出固化成禁止项，写进对应 skill |
| 受众定位（责任边界）| 受众栏 | 读者是谁，决定什么内容不许出现 |

**⑤ 产出与验收**：过程材料写作规范（每章：正文 or 表格）+ 反例清单 + 重新生成的对照样例。验收 —— 重新生成《报名表》，正文为主体、无开发口径、无空表格。

**⑥ 可引用的阶段成果**：过程材料支持「逐章指定形式」（哪一章写正文、哪一章写表格）；《报名表》去除开发口径并补上真人视角字段说明。

## 环节 7 · 架构升级决策

**本环节维度**：备选方案（A 微调 / B 加法式卡片工作流 / C 换技术栈重写）

**① 原始提问（原话照录）**

> 「能否将当前工作台做得更自由一些，就是说，人思考的少一些，结构也灵活一些，更像多个agent的集合体，不同agent完成不同任务？你先说行不行，先不要有大幅改动」
> 「查看这个工作台构建流程，你看看有哪些能够用在当前工作台设计，是否要加上vue等更专业的工具了：（微信公众号文章链接）」
> 「你来点大的如何？就设计成卡片拖拽工作流？然后每个卡片可以配置不同的引用资料，每个卡片都是一个agent，可以使用不同skill，通过引用和自己的再要求，让它输出合适的文本内容。你开始动手吧，大改结构都可以，只要不伤害已有功能。」

**② 结构化重写：这句话缺了哪些要素**

原话已含三层好意识：「先答行不行，别急着动」「外部资料要筛」「大改可以但不能伤已有功能」。缺的是：**候选取全**（只提了 Vue，没作比较）、**硬约束优先**（Vue 与零构建冲突）、**增量实施路径**（怎么大改还不出事）。

**③ 可整段复制的提示词（框架：ALIGN + 指令链，先评估后动手）**

```text
【第 1 段 · 只评估，不动手】
【角色】你是本项目的架构顾问。
```

## 3.2 MECE 自检（三问逐条回答）

**第 1 问 · 不重叠** —— 把任意两项拿来对比，有没有一件事能同时落进两格？

举例验证：第 17 条「自定义部分能加个删除的功能吗」与第 29 条「章节能不能动态删掉」**都是「删除」**，但被拆进了不同环节：
- 第 17 条落**环节 4**，因为它的对象是「技能包条目」（产出配置层）；
- 第 29 条落**环节 5**，因为它的对象是「存档里的材料章节字段」（数据层）。

判据是**对象不同**，不是动作不同 —— 若按「删除」这个动作归类，这两条就会重叠。

**第 2 问 · 不遗漏** —— 这一层所有项加起来，是不是等于上一层的全部？

34 条提问逐条归属，合计 3 + 5 + 5 + 3 + 6 + 1 + 3 + 6 + 2 = **34 条，无剩余项**（明细见 3.3）。
补充判据：**条数少不等于环节小** —— 环节 6 只有 1 条提问，但那一条里含 4 个独立问题（材料通篇铺表格 / 某些产出生成得莫名其妙 / 出现了不该出现的内容 / 要求 AI 自己先跑一遍）。

**第 3 问 · 同层级** —— 这些项是否处在同一个抽象高度？

8 个环节都处在「**工作推进的一段**」这一高度。反例说明：「往右挪一点」「字体贴着左边沿」这类**动作**没有单列成环，而是归入环节 5 的界面层 —— 若单列，它就和「模块化分解」不在同一层（一个是动作，一个是工作段）。
另：第 9 节「收束」是**元层**（把过程变成证据），不是工作推进的一段，故明确单列并加标注。

**停止判据**：拆到「可指派、可验收」就停 —— 每个环节的产出都能落成**一份文件或一组断言**，再往下拆只增加管理成本。

本项目的全部需求都产生于口语化沟通，我们按作业要求「完成过程中须在各个环节体现结构化思维模型的运用」，对沟通记录做了一次复盘式结构化：把整个建设过程 34 条原始提问，按**流程步骤**这一维度切成互斥且合计为全集的 8 个环节 —— ① 需求界定与目标定位、② 授权边界与环境自检、③ 概念澄清与信息架构、④ 模块化分解与技能包契约、⑤ 数据与呈现改造、⑥ 生成质量改造、⑦ 架构升级决策、⑧ 验证交付与文档，另设第 9 节作为元层收束。

每个环节都落实到具体的结构化模型，而不是停留在口号：**需求界定**用 5W2H 扫全要素，并用「硬约束 / 软约束」两栏把「只能在 demo2 内改动、不新增依赖」写成不可协商项；**概念澄清**坚持「先定义、再关系、后操作」，从而发现「产出」与「全周期任务」分属交付物维与时间维两条轴，据此重新划分了界面信息架构；**模块化分解**按「耦合度」一刀切，把 28 个技能包拆成 8 个结构技能与 20 类产出，并为用户自定义扩展定义了字段契约与非法格式的降级提示；**数据改造**把「活动时间」从一个时间点重构为「活动日期 + 分时段安排」两层，并确立「信息表只存哪几天、起止时间由第二层投影」的单一事实来源原则；**生成质量改造**用「问题—原因—对策」把「感觉不灵活」这类主观评价拆成可复现的最小用例，再把坏的输出固化为技能包里的禁止项；**架构升级**用决策矩阵在「微调 / 加法式改造 / 换技术栈重写」三案中取舍（加权得分 3.55 / 4.43 / 3.00，均为估算），并以硬约束一票否决了与「零构建零依赖」冲突的重写方案；**验证交付**按作业点名的「验证方案、验证指标、验证效果」三件套执行端到端走查，自动断言 32 个模块 855 项全部通过。

上述过程同时是 AI 赋能过程：需求澄清、代码改动、技能包改写、真机走查均由 AI 工具协作完成，人负责取舍与验收判据的确认。

# 第五部分 · 事实边界与局限（诚实声明）

1. **原始提问为原话照录**，未做美化；第 3.3 节可逐条核对。
2. **结构化重写属于「回溯包装」**：它诚实反映「每条需求最终被拆成了哪些结构要素」，但不声称当时就是按这段提示词逐条执行的。报告与汇报中的稳妥表述是：**「需求在推进过程中被逐步结构化，复盘时归纳为 8 类结构化提示词」**，不宜写成「当时即按此提示词执行」。
3. **所有数字均可复现**：`32 模块 / 855 项断言 / 失败 0`、`37 文件 / 945.6 KB / 34 个相对引用` 分别来自 `node tools/selftest.mjs` 与 `node tools/pack-static.mjs` 的实际输出，重跑即可得到。
4. **决策矩阵与手机打开成功率均为「估算」**，只作方案取舍依据，不作为实测结论。
5. **待确认项集中在第一部分第 7 节**，未做假设填充。
6. 本文件放在 `docs/` 下，**不参与静态打包**（`tools/pack-static.mjs` 明确排除 `docs/`），因此不会影响工作台产物的文件清单与体积。
