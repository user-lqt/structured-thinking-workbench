# 作业要求对照与 5 分钟课堂演示

核对日期：2026-10-10。依据工作区根目录《作业要求.md》。课堂汇报为 2026-10-13，每组共 8 分钟，其中 **5 分钟汇报、3 分钟提问与打分**。本稿采用本机 Node 服务和独立浏览器会话，不要求云部署。

## 1. 当前完成度与缺口

| 作业要求 | demo2 中已有的功能或资料 | 提交前需要补齐的证据 |
| --- | --- | --- |

| 5000 字以上总结报告 | 已有开发、提示词和验收文档可作为写作依据 | 当前工作区未找到正式总结报告；需包含摘要、正文、总结与思考、方案比较、结构化图、验证、问题解决和四人贡献 |

## 2. 优化优先级

### 必做

1. **压缩到 5 分钟。** 整体介绍、方案与方法、实机演示、验证与局限都须包含在这 5 分钟内。
2. **准备演示专用项目。** 从示例复制一份，预先完成宣传材料、执行手册和收尾三件套：复盘报告、经费决算表、资料归档清单。所有未真实发生的活动数据写明「模拟」。
3. **补齐正式提交物。** 总结报告、汇报 PPT、手册与提交目录；组号、成员姓名、具体贡献和真实活动数据由小组确认，不代填为事实。
4. **保留真实 AI 证据。** 建设过程和活动各阶段各选一个有代表性的案例，呈现「原始需求 → 结构化输入 → AI 输出 → 人工修订 → 最终成果」。现有提示词对照文档可作设计说明，整理后的提示词不能冒充当时实际对话记录。
5. **明确收尾闭环。** 签到时长只是执行记录。收尾还要对照目标与结果、核对费用、列出问题 / 改进责任人 / 下一次行动，并归档材料。

### 有余力再做

- 用一个成功案例加一个故障案例讲验证，例如正常同步与同时编辑冲突。
- 为现场操作准备截图或短录屏；保留 AI 输出成稿，避免现场等待生成。
- 排练期间核验实际 Word / Excel 文件能用课堂电脑上的软件打开，素材和链接能离线访问。

多人共享和考勤已做本机服务、独立浏览器与接口验证。按本次选定的演示方式，不必为了课堂再增加公网部署或真实手机扫码环节。

## 3. 演示前准备

1. 在仓库根目录运行 `node workbench/demo2/server.mjs`，打开 `http://127.0.0.1:4175/`，启动命令窗口保持打开。
2. 载入示例并复制为「课堂演示—校园科技文化节」，导出 JSON 作为排练前备份。
3. 普通浏览器作为组织者；项目库开启共享；隐私窗口通过成员邀请进入同一项目。普通浏览器的不同标签通常共享存储，独立浏览器或隐私会话更适合模拟另一位成员。
4. 预先填写一条参与者测试记录并签到，临场签退时可显示非零累计时长。普通参与者与工作人员各用自己的入口；工作人员身份和工作台编辑权限是两套概念。
5. 提前生成或手写并核验演示材料。若现场手写，就明确说明 AI 成果通过此前真实记录展示，不声称在实时生成。
6. 开好所需页面、收尾材料和导出文件。PPT 中放实际验证结果与截图；演示记录写清「模拟活动」，避免使观众误以为活动已经举办。

## 4. 5 分钟时间稿

| 时间 | 展示动作 | 讲述重点 |
| --- | --- | --- |
| 0:00–0:30 | PPT：问题与目标 | 大型活动常出现需求模糊、职责不清、材料分散和风险预案脱节；我们把事实、任务、材料和执行记录串起来 |
| 0:30–1:00 | PPT：一张全周期结构图 + 方案比较结论 | 展示四阶段分解、WBS、加权方案比选和风险矩阵；用报告里的真实方案比较说明为何选当前工作台 |
| 1:00–1:35 | 工作台：总览 → 全周期任务 | 一项任务的负责人、期限、依赖和产出，以及进入下一阶段前的检查点 |
| 1:35–2:15 | 风险预案：一项高风险 + 已有演练结论 | 触发信号是什么、谁处理、怎样预防和响应、何时升级；评分需要依据 |
| 2:15–2:55 | 卡片工作流 → 过程材料 | 展示已完成的「统一口径 → 参与者通知 / 工作人员岗位简报」，解释一次整理如何复用，出稿后人工核验并写入材料 |
| 2:55–3:25 | 切成员窗口修改一个地点字段，再看组织者同步 | 独立会话通过成员邀请协作；权限和版本冲突保护已有验证 |
| 3:25–3:55 | 参与者明细：签退预先签到的测试记录，切身份筛选 | 普通参与者与工作人员入口分开；展示首次签到、签退与已确认时长，不现场完整重复报名流程 |
| 3:55–4:25 | 过程材料：预先准备的复盘 / 决算 / 归档 | 执行记录用于核对目标和费用，改进项落实到责任人，材料可导出归档 |
| 4:25–5:00 | PPT：验证证据、分工与局限 | 报告验证方案和实际结果；四人贡献须真实；说明已验证本机服务，公网与实际校园手机网络未验证 |

讲述顺序为「为什么做 → 怎样拆解 → 怎样控制风险 → AI 如何复用资料 → 怎样协作与执行 → 怎样收尾与验证」。5 分钟内只走这条主线；二维码、全部菜单、冲突恢复详细步骤留到提问环节。

## 5. 验证怎么写入报告

截至前一轮验收，通过 **965 项离线断言、36 项 HTTP 集成检查、21 项真实浏览器检查**；接口测试覆盖同一出口 IP 的 215 条并发报名、200 条分页边界、幂等重试、身份隔离、邀请撤销、并发保存冲突与服务重启恢复。详见《多人共享与考勤验收》。这些是软件检查项数量，不是用户人数、满意度或活动效果评分。

报告中的验证表建议包含：场景、预期结果、执行方法、实际结果、证据文件、局限。浏览器和接口验证使用本机服务，AI 编排使用模拟响应；这不证明付费 AI 质量、真实手机扫码或公网可用。现场以真实配置为准。

活动模拟数据、软件测试数据与真实活动成果应分别标注。四人工作台使用角色不等于四位小组成员的建设贡献；总结报告需另外写明每个人负责的设计 / 开发 / 测试 / 资料工作及可核验成果。
