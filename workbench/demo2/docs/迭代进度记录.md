## R3 · 2026-10-04 第三轮：界面动效与设计工程打磨（依据 emilkowalski/skills）

依据 `emilkowalski/skills` 的 `emil-design-eng` 与 `review-animations`（含 `STANDARDS.md`）做了一次严格的动效审查与整改。改动只落在 `styles.css`，仍然零依赖、零构建、离线可用。

| Before | After | Why |
| --- | --- | --- |
| `transition: background 0.15s, border-color 0.15s, opacity 0.15s`（`.button`） | `transition: background / border-color / color 160ms ease, transform 120ms var(--ease-out)` | 内置 `ease` 对按压反馈太弱；按钮原本没有任何按下反馈 |
| 全站没有 `:active` 反馈 | `.button / .tab / .seg-switch button / .summary-chip / .quiet-icon / .row-remove / .mx-cell / .drill-step-line` 加 `transform: scale(0.95–0.97)`，120ms | 可按压元素需要「按下去」的物理反馈，这是标准里明确要求的一项 |
| `.mx-cell:hover { transform: translateY(-1px) }` 未加门禁 | 整段包进 `@media (hover: hover) and (pointer: fine)` | 触屏上 tap 会触发假 hover，出现「点一下跳一下」 |
| `.bar > i { transition: width 0.3s; }` | 删除。进度条每次由 `render()` 整段重建并直接带最终宽度，`width` 过渡永远不会触发 | 属于「动画布局属性（width）」+ 无效声明；整改优先级里删除排在第一位 |
| `.toast { transition: opacity 0.2s, transform 0.2s }`，进出同速、位移 20px | 出场 160ms / 入场 240ms，位移收到 12px，曲线统一 `var(--ease-out)` | 非对称节奏：系统响应要快、出现可以稍缓；用 `transition` 而非 keyframes，连续 toast 能被打断并重定向 |
| `.wizard` / `.login-gate` 用 `display: none` → `flex` 硬切 | 加 `opacity` + `@starting-style` + `transition-behavior: allow-discrete`；面板再叠一层 `scale(0.98 / 0.97)` 入场 | 模态属于「偶发」交互，值得一次正式出场；原本是凭空出现，没有任何过渡 |
| `#userMenu` 浮层 `display` 硬切、没有 origin | `transform-origin: top right` + `scale(0.96) translateY(-4px)` 入场 | 浮层应当从触发器的方向长出来；只有模态才允许从中心缩放 |
| 视图切换是瞬间整块替换 | `.panel` 增加 `panelIn` 200ms（`opacity` + `translateY(6px)`） | 只在面板由 `display: none` 变为可见时播一次，常规 `renderAll()` 重绘不会重放，不会影响输入时的高频重绘 |
| 完全没有 `prefers-reduced-motion` 处理 | 新增兜底块：缩短时长、去掉所有位移与缩放，保留 opacity 与颜色过渡 | 减少而不是清零；无系统动画偏好时仍然有可感知的过渡 |
| 只有输入框有焦点样式 | 对按钮 / 标签页 / 分段控件 / 图标按钮 / 项目切换补 `:focus-visible` 外框 | 键盘用户此前完全看不到焦点落在哪里 |
| `.ai-status` 只换颜色 | AI 工作时状态点加 1.1s 脉冲（`dotPulse`） | AI 生成可能跑十几秒，需要「还在跑」的状态指示 |

### 实现要点

- `:root` 新增动效令牌：`--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`、`--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`、`--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1)`，以及 `--dur-press: 120ms` / `--dur-quick: 160ms` / `--dur-enter: 200ms`。全站只动 `transform` 与 `opacity`，时长都在 300ms 以内。
- 入场统一走 `@starting-style`，不使用需要 JS 挂类名的方案；`allow-discrete` 让 `display` 也能参与过渡。
- 高频动作（标签切换、输入重绘）刻意保持轻量：面板入场只在切换时播放，没有任何交错（stagger）与逐元素动画，避免输入时掉帧。

### 一句话原理

电脑默认只监听 `127.0.0.1`；`cloudflared tunnel --url http://127.0.0.1:4175` 从本机主动往外连一条隧道，换回一个 `https://xxx.trycloudflare.com`，不用公网 IP、不用端口映射、命令一停地址就废。服务端把「带 `CF-Connecting-IP` / `X-Forwarded-For` / `X-Real-IP` 的请求」当成非本机，只放行填写页那几条路。工作台据此登记一个 4 位短码，二维码里只放短码，表单定义由本机按短码发给手机；手机提交的回执码按行落盘，工作台按 `since` 游标拉回来，折进表格走的还是 `mergeEvents`（按记录 id 幂等）。

## R27 · 2026-10-09 第二十七轮：把「待确认」从「数据」里摘出来（假阳性自动打勾 / 伪造的 0 / 向导主按钮在折叠线以下）

这一轮换了做法：不再只跑离线自测，而是**在真实浏览器里扮演一次用户**，从空项目把整条主线走完（选身份 → 向导填 3 个必填 → AI 补全信息表 → 生成任务分解 → 生成风险台账 → 提炼资源台账 → 生成过程材料 → 导出），边点边记哪里别扭。本轮的问题全是这一趟走出来的。

走查完发现，最要命的不是观感，而是**「待确认」这个词被下游当成了真数据**。AI 补空白时会写「待确认」，但它是给人看的标记，不是事实：

- `core/ai.js` 的数字字段归一化先 `replace(/[^\d.-]/g, '')` 再 `Number(...)`，而 `Number('')` 恰好是 `0`——于是模型对「预计人数」「预算上限」答「待确认」，库里就落下两个 `0`，界面上还标着「AI 建议」。一个看起来像事实的 0，比空着更有害。

- 只有 `core/risk.js` 单方面防过这个词，其它地方各写各的，**口径不统一**。

## R28 · 2026-10-09 第二十八轮：扫码前先自己说清「手机为什么连不上」（本机地址 / 只监听回环）

起因是一次真实报障：**「http://192.168.43.4:4175 这个手机扫码和 localhost 手机扫码都进不去」**。查下来是两个各占一半的原因叠在一起：

- `server.mjs` 默认只绑 `127.0.0.1`（这是有意的安全默认），手机的数据包根本到不了这个进程——`192.168.43.4:4175` 当然连不上；现场已用 `DEMO2_HOST=0.0.0.0` 重启并验证。
- 二维码里的地址取自「访问地址」；留空则跟随**当前网址**，于是电脑上生成的二维码编的是 `http://127.0.0.1:4175/signup.html`——同一个 `127.0.0.1`，在手机上指的是**手机自己**。所以「localhost 那张码」在手机上永远打不开。

真正的问题不在网络，而在**产品没说这句话**：两条路（隧道 / 局域网）的做法都写在「② 填写页与二维码」下面那段提示文字里，但整页没有任何一处能告诉使用者「你手上这张码，现在拿去扫是坏的」。所以这一轮不是补一句说明，而是让工作台**自己会判断**——把「链接地址 + 服务姿态」算成一个结论，再把结论写在二维码上方。

| 编号 | 改动 | 说明 |
| --- | --- | --- |
| R28-1 | 服务暴露自己的网络姿态（`server.mjs`） | 新增 `GET /api/net`（只允许本机，不在远程白名单里）：返回 `bind` / `port` / `lanOpen` / `lan[]`。`lan` 带网卡名与拼好的 URL，界面才有办法挑出 WLAN / 以太网那条，而不是把 VMware 的地址当成答案。启动日志里已有的「带网卡名逐条打印」现在也能被界面复用。 |

### R32 · 活动时间支持跨多天：哪天办、每天几点到几点，各填各的

## R46–R48 · 2026-10-10 第四十六至四十八轮：把画布的手感坑挖到底（文字被选中 / 按钮点了没反应 / 指针捕获抢走 click）

背景：R44–R45 补齐工具坞之后，使用者连报两条「看起来像坏了」的问题——「点击并拖动时，文本选中有问题，有时候会莫名其妙选中一堆文本，变得蓝蓝的」「卡片上的所有按钮按了没反应」。这两条都不是功能缺失，而是画布这种「手势密集」界面的接线问题：画布里每一次 pointerdown 既可能是「拖」、也可能是「点」，浏览器还要在你拖的时候顺手划词。

判断：不引任何库、也不改交互约定，只把「谁在什么时候接管指针」这件事讲清楚——**按下不等于拖动**。

| 编号 | 现象 | 根因 | 改法 |
| --- | --- | --- | --- |
| R46 | 拖动画布 / 卡片时，屏幕上莫名其妙出现一片蓝色选区（有时是半屏文字） | 画布里的节点就是普通 DOM 文字，`pointerdown` 之后浏览器按原生行为开始划词；而且选区不会因为松手自动收起，指针拖到画布外面（比如页面标题）照样在选 | `.flow-canvas` 整体 `user-select: none`（`.flow-canvas input / textarea / [contenteditable]` 例外，输入框仍可选中）；手势期间再给 `body` 挂 `is-gesturing`，`body.is-gesturing *` 全页 `!important` 禁选——指针拖出画布也不选；三条收尾路径（`pointerup` / `pointercancel` / 窗口 `blur`）都会摘掉标记 |
| R46b | 顺手修掉一个自己埋的雷：手势收尾过早清状态，会让「拖卡片落盘」「连线接上」偶发失效 | 早期版本在 `pointerup` 捕获阶段就把 `drag / pan / linking` 清空，`onCanvasUp` 再读就什么都没有了 | 拆成两个动作：`endGestureMark()` 只摘 `is-gesturing` 标记（`pointerup` 上挂），`resetGestureState()` 才清手势状态（只在 `pointercancel` / `blur` 用）；拖卡片与连线的收尾留在 `onCanvasUp` |
| R47 | 「卡片上的所有按钮按了都没反应」（运行 / 打开 / 收起 / 删除 / 看材料） | ① `startPan` 里的 `event.preventDefault()` 会掐掉画布内所有 `click`；② 手势通道先于按钮判断，按在按钮上也被当成平移的起点；③ 卡片底部「打开」按钮自己就带 `data-flow-open`，被 `closest('button, …')` 一刀切挡掉 | ① `startPan` 不再 `preventDefault`（禁选交给 R46 的 CSS）；② `onCanvasDown` 里工具坞、收起按钮优先放行，末尾再来一道 `closest('button, a, input, textarea, select, [data-flow-edge]')` 直接 return——按在按钮上只当点击，不做平移；③ `onCanvasClick` 放行 `control !== open && !control.dataset.flowOpen`，「打开」按钮重新能开配置窗 |
| R48 | R47 之后按钮「有时候还是没反应」，尤其是刚拖过卡片之后 | 用 CDP 打事件路径实测：`pointerdown` 阶段一旦执行 `setPointerCapture`，浏览器会把后续的 `pointerup / mouseup / click` **全部重定向到捕获元素**（日志里这三个事件的 target 都是画布面板 `panel`，卡片按钮根本收不到 click） | 指针捕获**推迟到真的拖起来**才做：按下时 `armCapture()` 只记一笔 `{panel, pointerId, x, y}`；`onCanvasMove` 里 `takeCapture()` 量到位移 ≥ 4px 才 `setPointerCapture`——点一下 = 一次干净的正常 click，拖起来 = 照常捕获。收手（`onCanvasUp`）、取消（`resetGestureState`）都会把待捕获状态清掉 |
